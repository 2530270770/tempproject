# NABC 立项卡

- 组号：T13
- 选题：B 需求—测试追溯一致性
- 成员：陈俊鹏、陈磊

## N（Need）

教师和助教需要回答“每条需求是否有通过用例、是否出现孤儿用例、需求变化后是否回归”。40 个左右仓库若靠人工交叉翻查，既慢又难以给出可复现的行号证据。系统需要只读、确定性地构建双向追溯关系。

## A（Approach）

系统按统一 Markdown 契约解析 FR/TC 和 covers 字段，以规则引擎建立 RTM，检测漏测、孤儿、重复、非法引用、关键用例缺口和全 FAIL 假覆盖；再用内容指纹比较基线与当前 SRS，通过受影响用例驱动变更回归状态机。CLI 输出标准 JSON 与 Markdown。

## B（Benefit）

助教可在固定 commit 上快速得到覆盖率、差异清单和文件行号，报告可重跑复核。学生能在提交前修正追溯缺口；教师只在真实争议和非结构化文本上投入人工判断。

## C（Competition）

GitLab 自带视图能展示文件和合并请求，但不理解 FR/TC 契约，也不判断 covers、关键边界和变更回归。与 A 的过程贡献统计、C 的 AI 留痕审计相比，B 专注“需求—测试”双向一致性和差异影响。

## 最关键硬规则

FAIL 用例不能计入覆盖；每条差异必须定位到编号和文件行号。

## L20 后最小可运行目标

给定含 FR/TC 的样例目录，能够输出 RTM，并准确报出 `FR-05` 漏测、`TC-22` 孤儿用例和关键 FR 缺边界用例。
