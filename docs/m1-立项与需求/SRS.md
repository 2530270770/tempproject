# 需求—测试追溯一致性检查器 SRS

SRS 版本: v2

## 1. 问题陈述

综合项目仓库包含需求、测试和大量过程材料。人工核对时容易出现三类问题：需求没有通过用例、用例引用了不存在的需求、需求变更后忘记回归。教师和助教需要在固定 commit 上快速得到可复核的双向追溯矩阵和差异清单。

系统只读取符合统一约定的仓库并提供客观证据，不评价用例设计质量，不执行被测系统测试，也不替代人工评审。

## 2. 干系人与系统边界

| 干系人 | 关心的问题 |
| --- | --- |
| 教师 | 配置阈值、查看全部报告、对争议做最终裁决 |
| 助教 | 批量检查、核对证据、确认变更回归 |
| 学生 | 查看本组 RTM、修复漏测/孤儿用例、提交回归证据 |

边界外系统是校内 GitLab、统一身份认证和可选的 AI 初筛服务。GitLab 提供文件与历史；统一认证提供已核验身份；AI 只能把非结构化关系的候选结果标为“待人工确认”。本系统不向被检查仓库写入内容。

## 3. 角色权限矩阵

| 功能 | 教师 | 助教 | 学生（本组） |
| --- | --- | --- | --- |
| 配置追溯阈值 | 可配置 | 只读 | 不可见 |
| 发起检查与重跑 | 可执行 | 可执行 | 不可执行 |
| 查看全部组报告 | 可执行 | 可执行 | 不可执行 |
| 查看本组 JSON/RTM | 可执行 | 可执行 | 只读 |
| 确认差异报告并归档 | 可执行 | 可执行 | 不可执行 |
| 修改基线或裁决争议 | 可执行 | 不可执行 | 不可执行 |

身份认证属于边界外系统。CLI 接收已经认证的角色和组号，并在业务层做拒绝检查；不把命令行参数当作可信登录凭证。学生不能发起检查、重跑或确认归档，只能在外部流程中提交本组回归证据，并查看教师或助教生成的组内 JSON/RTM。

## 4. 功能需求

| 编号 | 需求描述 | 优先级 | 验收标准 | 版本 |
| --- | --- | --- | --- | --- |
| FR-01 | 系统应从约定的 SRS Markdown 中解析 FR 编号、描述、优先级、验收标准和版本 | 必做 | 样例需求全部解析且定位到原文件行 | v1 |
| FR-02 | 系统应从 tests 目录解析 TC 编号、covers、类型、实际结果和验证版本 | 必做 | 全部 Markdown 用例被解析，非法 covers 不静默忽略 | v1 |
| FR-03 | 系统应识别没有至少一条 PASS 用例覆盖的 FR | critical | 报 MISSING_TEST 并指向 FR 行号 | v1 |
| FR-04 | 系统应识别 covers 引用不存在 FR 的孤儿用例 | critical | 报 ORPHAN_TEST 并指向 TC 行号 | v1 |
| FR-05 | 系统应识别重复 FR/TC 编号、重复用例内容和非法 covers | 必做 | 重复编号报 DUP_ID，重复用例报 DUP_TEST；covers 为空或不符合 FR-xx 格式报 BAD_REF；格式合法但 FR 不存在报 ORPHAN_TEST；三类输入分别有断言样例 | v1 |
| FR-06 | 系统应校验关键 FR 同时具有 PASS 的正常用例和边界用例 | critical | 缺任一类分别报 CRITICAL_NO_HAPPY 或 CRITICAL_NO_BOUNDARY | v1 |
| FR-07 | 系统不得把 FAIL 用例计为覆盖，应识别被标为已覆盖但关联用例全部 FAIL 的 FR | 必做 | 该 FR 不计入覆盖并报 TEST_ALL_FAIL_MARKED_COVERED；只有至少一条 PASS 的 FR 才计入覆盖 | v1 |
| FR-08 | 系统应比较基线与当前 SRS 的 FR 修改、删除和新增并分析受影响用例 | critical | 输出 changed_fr、affected_tests、pending，并报 NEED_REGRESSION；关联用例置“待回归”，回归完成且验证版本匹配后闭环 | v1 |
| FR-09 | 系统应输出统一字段 JSON、双向 RTM Markdown 和差异清单 | 必做 | JSON 至少含 team_id、project、commit、checked_at、read_only 和 issues；每个 issue 含 code、severity、evidence，并按适用情况提供 ref、file、line；RTM 同时列需求和用例关系 | v1 |
| FR-10 | 系统应为每条差异给出一条可定位证据 | critical | 每条 issue 至少包含 ref、file、line 或明确文档位置 | v1 |
| FR-11 | 系统应在同一输入上产生相同结论和同一组问题 | 必做 | 去除检查时间后两次 JSON 完全一致 | v1 |
| FR-12 | 系统应按角色和组号限制检查、确认和跨组查看 | 必做 | 未授权动作被拒绝并给出原因 | v1 |
| FR-13 | 系统应输出覆盖矩阵和覆盖率统计 | 必做 | 矩阵覆盖/未覆盖/孤儿/重复分类正确；输出 FR 覆盖率及关键 FR 正常/边界覆盖率；固定样例数值正确且每项可定位到 FR/TC | v1 |
| FR-14 | 系统只依据显式结构化关系作确定判断；对非结构化输入或可选 AI 候选关系，必须交由人工确认 | 应做 | 非结构化输入不生成确定覆盖结论；候选关系在人工确认前不得计入覆盖率或差异结果 | v2 |

## 5. 关键用例

### UC-01 标准 bad 样例检查

1. 助教指定目标仓库、当前 SRS 和 tests。
2. 系统解析结构化条目并执行追溯规则。
3. 系统输出 FR-05 漏测、FR-02 缺边界用例、TC-22 孤儿用例及行号证据，并输出覆盖矩阵与 FR/关键覆盖统计。
4. 助教核对后可确认并归档。

异常流：

- SRS 或 tests 为空：任务进入“异常待人工”，不输出虚假全绿。
- 仓库不可达：明确报告路径或克隆错误，保留只读边界。
- AI 对非结构化内容给出候选关系：全部标为“待人工确认”，确认前不计入覆盖率或确定差异。

### UC-02 需求变更回归

1. 助教提供基线 SRS 或 `--baseline-ref`。
2. 系统比较 FR 内容指纹，列出修改和删除项。
3. 系统通过 covers 找到受影响 TC；验证版本不等于当前 SRS 版本的用例进入待回归。
4. 用例完成回归并更新验证版本后，再次检查可闭环。

## 6. 可度量质量需求

| 编号 | 类别 | 可度量指标 | 如何度量 |
| --- | --- | --- | --- |
| NFR-01 | 功能正确性 | 结构化 good/bad 样例的问题码判定准确率为 100% | 固定夹具逐项断言期望问题码，误报和漏报均为失败 |
| NFR-02 | 性能效率 | 100 条 FR、300 条 TC 从解析到报告不超过 10 秒 | 同一输入计时 5 次，报告中位数 |
| NFR-03 | 可靠性 | 同一 commit 重跑结论一致 | 去掉 checked_at 后比较两次 JSON，差值应为 0 |
| NFR-04 | 可核对性 | 100% issue 含 code、severity、ref、file、line，误报可通过原文件复核 | 对固定样例逐条检查字段完整性，并按 ref/file/line 回到原条目核验 |
| NFR-05 | 诚实边界 | 非结构化输入或 AI 初抽关系 100% 标记“待人工确认”，确认前不输出确定覆盖率和差异结论 | 对 AI 候选关系检查状态字段；人工确认前后分别生成报告并比较，确认前不得影响覆盖 |

## 7. 明确不做

- 不执行被检查仓库的构建、测试、覆盖率或 lint。
- 不评价测试能否发现真实缺陷，不按行数或 AI 比例打分。
- 不对任意自然语言自动给出确定的追溯结论。
- 不做过程贡献统计（A）或 AI 留痕合规（C）。
- 不修改、修复或向被检查仓库提交任何内容。
