# 架构决策记录

## ADR-001：采用单机可复现 CLI 作为核心交付形态

- 状态：已接受
- 背景：系统需在 5 周内由不超过 4 人完成，主要处理约 100 条 FR、300 条 TC 的结构化文件，并保证同一 commit 可复现。课程不提供 CI Runner，场景为学期一次性评阅。
- 候选方案：
  1. 单机 Python CLI，文件输入输出，无数据库。
  2. Web 服务、关系数据库和前端看板。
  3. 微服务、消息总线、注册中心和多数据库。
- 决策：选择方案 1。解析、规则引擎、三个状态机和报告写入均为确定性本地构件；远端仓库仅作为只读输入，不增加常驻服务。
- 后果：收益是部署成本低、离线可演示、行号证据稳定、测试容易复现；代价是没有内置多用户登录和在线看板。身份与 GitLab 访问由边界外系统提供，报告可由 A 看板消费。
- 重评信号：若并发助教超过 20 人、需要长期保存和检索 10 万级报告、或要求在线审批流与细粒度权限，则评估 Web 服务；若单仓库解析超过性能预算且需横向扩容，再评估异步队列。

## ADR-002：用规范化内容指纹判断需求变更

- 状态：已接受
- 背景：仅比较版本字段会把格式化变化误判为需求变化；仅比较原文又会对无意义空白产生回归噪音。
- 候选方案：直接 diff 文件；比较版本字符串；比较规范化语义字段指纹。
- 决策：比较 `title + description + acceptance + priority` 去除空白后的 SHA-256 指纹，版本号用于判断用例是否已完成新版本回归。
- 后果：可稳定识别内容变化，忽略排版差异；代价是字段拆分依赖约定格式。
- 重评信号：若 SRS 改为具备稳定条目级 ID 的数据库，则改用字段级版本与审计日志。
